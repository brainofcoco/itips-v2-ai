# V2 Deployment Runbook

Audience: the engineer flashing a Jetson and installing it at a tower site.

> Prerequisite reading: `README.md` (what it is), `ARCHITECTURE.md` (how it
> fits together), `RULE.md` (how we work).

---

## 1. One-time per-Jetson preparation

### 1.1 Flash JetPack

Flash the Jetson Orin Nano Super Developer Kit with **JetPack 6.x**
using NVIDIA SDK Manager. Confirm `nvidia-smi` works after first boot.

### 1.2 Verify CUDA + GStreamer

```bash
python3 - <<'PY'
import cv2, torch
print("torch.cuda:", torch.cuda.is_available())
print("gstreamer:", "GStreamer:" in cv2.getBuildInformation() and "YES" in cv2.getBuildInformation())
PY
```

Both must report true. If GStreamer is missing, the L4T-ML container will
provide it — but the host check should still pass.

### 1.3 Mount the NVMe SSD

```bash
sudo mkfs.ext4 /dev/nvme0n1
sudo mkdir -p /opt/itips
sudo mount /dev/nvme0n1 /opt/itips
echo "/dev/nvme0n1  /opt/itips  ext4  defaults,nofail  0 2" | sudo tee -a /etc/fstab
```

Three directories live on the NVMe and are bind-mounted into the container:

- `/opt/itips/evidence_store` — signed incident packages
- `/opt/itips/dataset` — enrolled face gallery
- `/opt/itips/var` — `intake.sqlite`, logs, runtime state
- `/opt/itips/models` — YOLO + TensorRT engines

## 2. Per-site configuration

### 2.1 Copy the environment template

```bash
cd /opt/itips
git clone https://github.com/Seismic-Consulting-Limited/ITIPS-ai.git
cd ITIPS-ai/v2
cp .env.example .env
```

### 2.2 Fill in the per-site values

Open `.env` in whichever editor you have installed:

```bash
nano .env          # ships with macOS and most Linuxes
vim .env           # if you prefer modal editing
code .env          # VS Code
open -e .env       # macOS TextEdit
```

The mandatory keys for production:

- `ITIPS_SITE_ID` — UUID from the site registry
- `ITIPS_OPERATOR_ID` — UUID from the operator registry (towerco)
- `ITIPS_DEVICE_ID` — Jetson serial
- `ITIPS_SITE_LATITUDE`, `ITIPS_SITE_LONGITUDE`
- `ITIPS_CAMERA_*_RTSP` — per-camera URLs with credentials
- `AXPRO_HOST`, `AXPRO_USERNAME`, `AXPRO_PASSWORD`
- `ITIPS_INBOUND_TOKEN` — generated by the backend on device provisioning
- `ITIPS_DEVICE_HMAC_KEY` — 64 hex chars, generated once per device

`.env` is **never committed**. The CI pipeline ships `.env.example` only.

### 2.3 Convert the YOLO model to TensorRT (once per Jetson)

```bash
./scripts/export_yolo_tensorrt.sh
```

This downloads `yolo11n.pt`, exports it to `yolo11n.engine` at FP16, and
places it under `/opt/itips/models/`. The engine is architecture-specific —
do not copy across machines.

## 3. Run

### 3.1 Production (on the Jetson)

```bash
make build
make up
make logs
```

The container exposes:

- `:5050` — MJPEG live feeds, SSE alert stream, evidence retrieval, ops UI
- `:8443` — inbound backend API (bearer token; mTLS in Phase 1)

### 3.2 Simulation (on a dev laptop, no GPU required)

```bash
make sim
```

`docker-compose.sim.yml` adds:

- A **MediaMTX** container that serves looped MP4 files as RTSP streams.
- An **ffmpeg looper** that publishes test footage from `assets/sim/*.mp4`
  into MediaMTX.
- The ITIPS container with `ITIPS_SIMULATE=true`, which lets the CUDA guard
  pass on CPU and uses smaller models.

Drop your own MP4 fixtures into `assets/sim/` to extend the simulation.

## 4. Health checks

```bash
curl -fsS http://localhost:5050/health     # liveness
curl -fsS http://localhost:5050/status     # detailed status JSON
./scripts/healthcheck.sh                   # full end-to-end probe
```

The backend's Device Management Service watches the A1 heartbeat record in
the intake queue. If we publish three A1 packets and none drain, the backend
flags the device as offline.

---

## 5. Updates

For POC and Phase 1, updates are done by `make pull && make up`. Zero-touch
firmware rollout (B5 endpoint) is implemented in V2 but the staged-rollout
controller lives in the backend Device Management Service.

---

## 6. Decommission

```bash
make down
sudo umount /opt/itips
# physical removal of Jetson per site decommission checklist
```

`evidence_store/` must be preserved per CNII evidence-retention policy —
copy it off the NVMe before reformatting.
